    mds写入失败

    2025/11/09 - ceph 集群 cephfs 故障处理

    出现 1 clients failing to respond to cache pressure

    1 clients failing to respond to cache pressure 表示：有 1 个 Ceph 客户端（如挂载 Ceph 文件系统的服务器、使用 RBD 的虚拟机、调用 RGW 的应用等）没有响应 Ceph 集群发送的 “缓存压力调节请求”。

    Ceph 的 OSD（对象存储守护进程）会使用系统缓存（页缓存、BlueStore 缓存等）加速数据读写。当 OSD 的缓存使用率过高（比如接近阈值）时，集群会主动向客户端发送 “缓存压力通知（cache pressure hints）”，目的是：

    • 让客户端减少缓存占用（比如主动 flush 脏数据到集群、降低读写请求的缓存依赖）；
    • 避免 OSD 缓存溢出导致性能骤降、IO 阻塞或集群不稳定。
      正常情况下，客户端收到通知后会配合调整；而这个告警的核心是：有 1 个客户端没按预期配合，导致集群无法通过客户端侧缓解 OSD 的缓存压力。

    主要问题出现在客户端，需要排查

    1. 检查ceph详细健康状态 ceph health detail可以看到哪个客户端有问题
    2. 检查客户端使用的ceph版本是否和服务器的版本匹配，或者兼容
    3. 客户端是否无响应

    一般情况下不用管，只需要持续监控 mds 服务是否正常即可

    如果长时间无法恢复

    ceph mds client recall 5576386  # 强制触发客户端缓存回收
ceph mds client evict 5576386  # 若回收无效，直接断开客户端连接（需确认客户端可重启）

    
# 查看 recall_caps 字段
ceph tell mds.${id} session ls

    我统计了所有对象前缀，发现rbd_data.395060268cf494就是这个最多，基本就是8.8Ti的数据量，可以确定是这个

    现在问题根源已经找到，就是孤儿对象前缀

    1. 那么为什么rbd du 不显示？
    • rbd du只读取元数据正确的镜像（通过rbd_id.<name>→rbd_header.<id>→rbd_data.<id> 追踪）
    • rbd_data.395060268cf494的元数据（rbd_id.*和rbd_header.395060268cf494）已不存在

    1. 为什么会出现？（CSI典型场景）
      当 Kubernetes 删除 PVC 时：

    2. CSI 调用rbd rm 删除镜像

    3. 元数据成功删除（rbd_id和rbd_header 被删）

    4. 数据对象删除失败（OSD 响应超时、网络中断、OSD 宕机）

    5. 结果是：镜像消失，数据残留

    6. 为什么rbd trash ls 为空？
      因为 CSI 的 rbd rm 直接删除，不经过 trash。trash 只包含 rbd trash move 命令移入的镜像。

    通过脚本批量删除的方式，来对孤儿对象进行删除

    # 确认该前缀没有对应任何现有镜像
rbd ls -p rbd-pool | while read img; do
  rbd info -p rbd-pool $img | grep "id: "
done | grep 395060268cf494

    
# 先将之前导出的 rados ls -p rbd-pool 的文件 rbd-pool-objects 提取孤儿对象前缀，手动确认，避免删除
grep rbd_data.395060268cf494 rbd-pool-objects  > need_to_delete_objects

    
# 然后脚本批量删除，选个性能好的机器
cat > cleanup_orphan.sh <<'EOF'
#!/bin/bash
POOL="rbd-pool"
PREFIX="rbd_data.395060268cf494"
BATCH_SIZE=1000
WORKERS=32
OBJECTS_FILE="need_to_delete_objects"

    
echo "Starting cleanup of orphan prefix: $PREFIX"
echo "Total objects: $(wc -l < "$OBJECTS_FILE")"

    
# 从文件读取对象列表并分批删除
cat "$OBJECTS_FILE" | \
  xargs -P $WORKERS -n $BATCH_SIZE -I {} bash -c "
    if ! rados rm -p $POOL '{}'; then
      echo 'FAILED: {}' >&2
      echo '{}' >> 'failed_objects.txt'
    fi"

    
echo "Cleanup completed."
EOF

nohup ./cleanup_orphan.sh > cleanup_orphan.log 2>&1 &

    作用 使用场景
    noup 防止OSD进程启动后自动标记为（up）状态 防止OSD反复重启，常用于调试
    nodown 忽略OSD宕机报告，防止其标记为（down）状态 网络故障排除
    noin 防止OSD在启动后自动加入集群（in）状态 需要手动确认OSD健康后再让其加入
    noout 最重要，防止OSD宕机超时后自动标记为out（移出集群）而避免不必要的数据迁移 主机维护、计划内停机、磁盘更换
