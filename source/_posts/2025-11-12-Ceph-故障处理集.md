### 出现 1 clients failing to respond to cache pressure

`1 clients failing to respond to cache pressure` 表示：**有 1 个 Ceph 客户端（如挂载 Ceph 文件系统的服务器、使用 RBD 的虚拟机、调用 RGW 的应用等）没有响应 Ceph 集群发送的 “缓存压力调节请求”**。

Ceph 的 OSD（对象存储守护进程）会使用系统缓存（页缓存、BlueStore 缓存等）加速数据读写。当 OSD 的缓存使用率过高（比如接近阈值）时，集群会主动向客户端发送 **“缓存压力通知（cache pressure hints）”**，目的是：

- 让客户端减少缓存占用（比如主动 flush 脏数据到集群、降低读写请求的缓存依赖）；
- 避免 OSD 缓存溢出导致性能骤降、IO 阻塞或集群不稳定。
正常情况下，客户端收到通知后会配合调整；而这个告警的核心是：**有 1 个客户端没按预期配合，导致集群无法通过客户端侧缓解 OSD 的缓存压力**。

主要问题出现在客户端，需要排查

1. 检查ceph详细健康状态 `ceph health detail`可以看到哪个客户端有问题
2. 检查客户端使用的ceph版本是否和服务器的版本匹配，或者兼容
3. 客户端是否无响应

一般情况下不用管，只需要持续监控 mds 服务是否正常即可

如果长时间无法恢复

```Bash
ceph mds client recall 5576386  # 强制触发客户端缓存回收
ceph mds client evict 5576386  # 若回收无效，直接断开客户端连接（需确认客户端可重启）
```

我统计了所有对象前缀，发现rbd_data.395060268cf494就是这个最多，基本就是8.8Ti的数据量，可以确定是这个

现在问题根源已经找到，就是孤儿对象前缀

1. 那么为什么rbd du 不显示？
- `rbd du`只读取**元数据正确的镜像**（通过`rbd_id.<name>`→`rbd_header.<id>`→`rbd_data.<id>` 追踪）
- `rbd_data.395060268cf494`的元数据（`rbd_id.*`和`rbd_header.395060268cf494`）**已不存在**

1. 为什么会出现？（CSI典型场景）
当 Kubernetes 删除 PVC 时：

1. CSI 调用`rbd rm` 删除镜像
2. 元数据成功删除（`rbd_id`和`rbd_header` 被删）
3. **数据对象删除失败**（OSD 响应超时、网络中断、OSD 宕机）
4. 结果是：**镜像消失，数据残留**

1. 为什么`rbd trash ls `为空？
因为 CSI 的 `rbd rm` 直接删除，**不经过 trash**。trash 只包含 `rbd trash move` 命令移入的镜像。

通过脚本批量删除的方式，来对孤儿对象进行删除

```Bash
# 确认该前缀没有对应任何现有镜像
rbd ls -p rbd-pool | while read img; do
  rbd info -p rbd-pool $img | grep "id: "
done | grep 395060268cf494

# 先将之前导出的 rados ls -p rbd-pool 的文件 rbd-pool-objects 提取孤儿对象前缀，手动确认，避免删除
grep rbd_data.395060268cf494 rbd-pool-objects  > need_to_delete_objects

# 然后脚本批量删除，选个性能好的机器
cat > cleanup_orphan.sh <<'EOF'
#!/bin/bash
POOL="rbd-pool"
PREFIX="rbd_data.395060268cf494"
BATCH_SIZE=1000
WORKERS=32
OBJECTS_FILE="need_to_delete_objects"

echo "Starting cleanup of orphan prefix: $PREFIX"
echo "Total objects: $(wc -l < "$OBJECTS_FILE")"

# 从文件读取对象列表并分批删除
cat "$OBJECTS_FILE" | \
  xargs -P $WORKERS -n $BATCH_SIZE -I {} bash -c "
    if ! rados rm -p $POOL '{}'; then
      echo 'FAILED: {}' >&2
      echo '{}' >> 'failed_objects.txt'
    fi"

echo "Cleanup completed."
EOF

chmod +x cleanup_orphan.sh
nohup ./cleanup_orphan.sh > cleanup_orphan.log 2>&1 &
```

### 添加OSD的时候，出现noout标识

```Bash
root@:~# ceph health detail
HEALTH_WARN 1 OSDs or CRUSH {nodes, device-classes} have {NOUP,NODOWN,NOIN,NOOUT} flags set
[WRN] OSD_FLAGS: 1 OSDs or CRUSH {nodes, device-classes} have {NOUP,NODOWN,NOIN,NOOUT} flags set
    host ceph-store-01 has flags noout
```

这个其实是ceph的管理方式，有可能是rook-ceph调整后没有恢复，可以手动恢复

|  | 作用 | 使用场景 |
| --- | --- | --- |
| noup | 防止OSD进程启动后自动标记为（up）状态 | 防止OSD反复重启，常用于调试 |
| nodown | 忽略OSD宕机报告，防止其标记为（down）状态 | 网络故障排除 |
| noin | 防止OSD在启动后自动加入集群（in）状态 | 需要手动确认OSD健康后再让其加入 |
| noout | 最重要，防止OSD宕机超时后自动标记为out（移出集群）而避免不必要的数据迁移 | 主机维护、计划内停机、磁盘更换 |

```Bash

ceph osd set-group <flag-name> <who> # who 可以是osd或者node

# 手动移除flag

ceph osd unset-group <flag-name> <who> # who 可以是osd或者node
```

### rook-ceph删除cephfs

在 Rook-Ceph 里把 CephFileSystem（CephFS）彻底删掉，需要按“业务 → Rook → Ceph”三个层次倒序清理

- 业务侧清理
```Bash
# 删除掉用到Cephfs的Pod和PVC
kubectl delete pvc -A --selector \
-l "volume.beta.kubernetes.io/storage-class in (rook-cephfs,csi-cephfs)"

# 删除掉快照
kubectl delete volumesnapshot -A --all
kubectl delete volumesnapshotcontent -A --all
```

- 清理Rook层（SC → CephFilesystemSubVolumeGroup → CephFilesystem）
```Markdown
# sc
kubectl delete sc rook-cephfs

# 删除subvolumeGroup
kubectl -n rook-ceph delete cephfilesystemsubvolumegroup csi

# 删除CephFilesystem本体
kubectl -n rook-ceph delete cephfilesystem myfs
```

这一步最容易卡住：

- 如果 subvolumeGroup 状态一直 Progressing，先确认上面所有 PVC、Pod 已释放；
- 仍卡住的，把 finalizer 手动置空：
  ```YAML
  kubectl -n rook-ceph patch cephfilesystemsubvolumegroup csi \
  --type merge -p '{"metadata":{"finalizers":[]}}'
  kubectl -n rook-ceph patch cephfilesystem myfs \
  --type merge -p '{"metadata":{"finalizers":[]}}'
  ```

- 清理Ceph层（pool）
```Bash
# 删除文件系统
ceph fs set myfs down true
ceph fs rm myfs --yes-i-really-mean-it

# 删除池
ceph osd pool rm myfs-replicated myfs-replicated --yes-i-really-really-mean-it
ceph osd pool rm myfs-metadata myfs-metadata --yes-i-really-really-mean-it
```

### RBD镜像锁竞争问题

常出现在k8s调度，前一个还没有释放，后一个已经要加进来了

```Bash
-device-type krbd --options noudev], rbd error output: rbd: sysfs write failed
rbd: map failed: (13)Permission denied
```

- 根本原因是节点尝试挂载的时候，需要**打破旧锁**，并将旧客户端加入黑名单(blocklist)
- 但是没有足够的执行权限去操作blocklist

但是要操作blocklist 是需要mon的rwx权限的，太大了

所以可以手动清理旧锁，或者干脆等待，有时候需要20分钟才能释放

```Markdown
# 在 Ceph 管理节点查看当前锁持有者
rbd lock list rbd-pool/csi-vol-8c3ebf79-7971-4c02-b16f-5bac050cd9b6

# 查看当前客户端列表
rbd status rbd-pool/csi-vol-8c3ebf79-7971-4c02-b16f-5bac050cd9b6

# 手动 blocklist 旧客户端（需要 admin 权限）
ceph osd blocklist add 10.0.0.xxx  # client42790400 对应的 IP
ceph osd blocklist add 10.10.128.223:0/3360680447

# 或者解除镜像锁（如果确定旧客户端已死）
rbd lock remove rbd-pool/csi-vol-8c3ebf79-7971-4c02-b16f-5bac050cd9b6 <lock-id> client42790400

rbd lock remove rbd-pool/csi-vol-8c3ebf79-7971-4c02-b16f-5bac050cd9b6 "auto 18446462598732840961" client.45160975
```
